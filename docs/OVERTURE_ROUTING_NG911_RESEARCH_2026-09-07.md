# Overture routing, contributions, and NG911 foundation research

Research date: 2026-09-07. This report distinguishes verified upstream capabilities from proposed product work. Documentation and upstream repositories were inspected; no routing engine, dataset conversion, or operational NG911 integration was executed. Recommendations need a bounded regional pilot and version-pinned compatibility tests.

## Recommended direction

Build three connected workflows on the same cloud-data and local-review foundation: **Explore data**, **Build a study network**, and **Prepare an NG911 foundation**. Add **Suggest a correction** to feature inspection. Keep Overture releases immutable; store local edits, evidence, review decisions, and agency data separately with explicit links back to source features. This supports normal ArcGIS editing without pretending edits immediately change the shared basemap.

Prioritize reliable extraction, provenance, schema adaptation, and editable review layers before adding routing or NG911 exports. The public-safety opportunity is to reduce expensive preparation and expose missing evidence. A generated foundation must not be presented as dispatch-ready data or a substitute for the responsible authority's acceptance process.

## Routing correctness before routing speed

**Verified:** connectivity comes from shared connector IDs, including connectors inside a segment. Intersecting geometry or coincident coordinates do not establish connectivity by themselves. Segment `level` describes visual stacking and is not precise elevation; differently leveled segments can connect. [Segments and connectors](https://docs.overturemaps.org/guides/transportation/segments-and-connectors/)

**Verified:** road access can depend on heading, vehicle mode, dimensions, and time. Road-class and local defaults matter when explicit rules do not apply. `prohibited_transitions` contains simple and via turn restrictions. Flattening these to a speed and one-way field loses meaning. [Roads](https://docs.overturemaps.org/guides/transportation/roads/), [Scoping and travel modes](https://docs.overturemaps.org/guides/transportation/scoping-and-travel-modes/)

**Verified:** Overture's `at` and `between` values are normalized using WGS84 ellipsoidal distance. Planar longitude/latitude length is not the documented convention. [Linear referencing](https://docs.overturemaps.org/guides/transportation/linear-referencing/)

**Proposed implementation contract:**

1. Extract a buffered study area, retain complete segment geometries, and resolve referenced connectors and transition paths. Flag unresolved dependencies and the boundary where routes are truncated. Clipping geometries before interpreting normalized measures changes their meaning.
2. Produce an engine-neutral graph package: nodes, directed edges, turn paths, conditional rules, costs, and source crosswalk. Keep `(release, source_segment_id, start_measure, end_measure, direction)` for traceability; generated split-edge IDs are local IDs, not newly assigned GERS IDs.
3. Split at connector measures and cost/restriction breakpoints as needed by the target engine. Evaluate direction and rule scope consistently. Reject unsupported semantics or expose affected edges clearly; do not silently discard restrictions.
4. Cache by release, study area, adapter version, routing profile, and local-overlay revision. Update only after a successful build and preserve the previous working package. Start with complete regional rebuilds; incremental tile updates come after dependency invalidation is proven.
5. Present missing speeds separately from measured/posted values. Any class-based speed assumption should remain visible in route and travel-time output. Emergency access exceptions require an agency-defined profile; never derive blanket exemptions from the application being used for emergency planning.

Proposed acceptance fixtures: internal junction; grade-separated crossing; on-ramp; roundabout; cul-de-sac; simple and via turn restriction; direction-scoped access; timed closure; vehicle height/weight restriction; ferry; AOI edge; missing connector; unknown speed; and a local correction invalidated by a new release. Compare route paths and restriction violations, not merely whether a route exists. Measure cold extraction time, bytes fetched, peak memory, graph build time, warm solve latency, and offline repeatability.

## A practical path to better shared data

**Verified:** Overture directs reproducible data problems to its public issue tracker and asks for the release, reproducing query, entity IDs or bounds, and relevant screenshots. Organizations interested in open-data contributions can contact Overture. These documented channels are not a general feature-edit transaction API, and no guaranteed acceptance or resolution time is documented. [Support](https://docs.overturemaps.org/support/), [Contribution FAQ](https://overturemaps.org/about/faq/)

**Proposed first release:** a correction workspace containing the original feature, proposed geometry/attributes, reason, evidence reference, source date, submitter organization, proposed license, and local review status. Provide a side-by-side map and changed-field table. Generate a reproducible issue package with release/GERS/source IDs, bounds, screenshots, and a minimal query. Generate drafts locally; external publication remains an explicit user action.

**Proposed later release:** support organization-scale contributions with schema validation, duplicate/match review, change summaries, and packaging agreed with Overture. Use bridge files and source attribution to suggest the relevant upstream route, including OSM where applicable. A proposed Overture correction does not guarantee a change in OSM or any other upstream dataset. Track submitted, acknowledged, accepted, incorporated, and verified-in-release as distinct states.

**Extensions:** begin with a documented local enrichment package keyed to source entities, including original release and match evidence. This follows GERS' documented ability to associate independent data. Propose generally useful public fields upstream through the schema repository; keep local review state, agency operational attributes, and restricted evidence in their own governed tables. This is a proposed add-in profile, not an officially recognized Overture NG911 schema. [GERS association](https://docs.overturemaps.org/gers/), [Schema repository](https://github.com/OvertureMaps/schema)

**Licensing fact:** Overture transportation, buildings, divisions, and base themes are currently documented under ODbL; addresses have varied source terms and places use other licenses. Preserve theme/source attribution and evaluate rights for the actual derived product and contribution package. A separate table alone does not establish legal independence from a derived database. [Attribution and licensing](https://docs.overturemaps.org/attribution/)

## NG911 foundation: what to build and what remains authoritative

**Verified current standard:** NENA-STA-006.3-2026 was approved by the NENA Board on March 11, 2026. It requires road centerlines and Site/Structure Address Points; the latter layer's required status does not impose complete coverage. It specifies primary PSAP and primary police/fire/EMS service boundaries, and a provisioning boundary. The standard distinguishes fields that are required, conditional, or optional, and includes updated layer names, identifiers, and relational structures. Required road attributes include sided address ranges and parity. Local addressing authorities determine the primary street/address names. The responsible 9-1-1 Authority remains responsible for data within its service area. Implement against the current standard and the receiving jurisdiction/provider profile; older v2 templates are not sufficient evidence of v3 conformance. [NENA GIS Data Model v3, especially sections 4.1–4.4](https://cdn.ymaws.com/www.nena.org/resource/resmgr/standards/nena-sta-006.3_ng9-1-1_gis_d.pdf)

**Verified distinction:** NG911 location validation and call routing depend on authoritative GIS and service boundaries. A street travel path is a different product from determining the correct destination for an emergency call. Federal guidance emphasizes GIS/911 coordination, boundary agreement with neighbors, and ongoing stewardship. [National 911 Program: required entities](https://www.911.gov/assets/NHTSA-GIS_Current-Status-of-Required-Entities-_MAR2023_Final.pdf), [GIS technologies](https://www.911.gov/assets/NHTSA-GIS_Project-Current-Status-of-911-GIS-Technologies_MAR2023_Final.pdf)

**Useful open inputs:** USDOT's National Address Database aggregates state/local/tribal addresses, with uneven coverage and no accuracy/completeness/suitability warranty. It is useful for candidate matching and gaps, but freshness must be checked against the original authority. State and local NG911 GIS programs may expose better sources; North Carolina documents an authoritative NG911 centerline service. Availability and reuse conditions must be checked per dataset and jurisdiction. [NAD terms and limitations](https://www.transportation.gov/mission/open/gis/national-address-database/national-address-database-nad-disclaimer), [NC transportation service](https://services.gis.nc.gov/secure/rest/services/NC1Map_Transportation/MapServer)

### Proposed guided workflow

1. **Choose the authority and target.** Record the jurisdiction, responsible steward, adopted schema/profile, receiving system, and source date. The wizard should explain the data needed in ordinary language and identify missing source owners.
2. **Inventory existing local data first.** Match it to Overture roads, addresses, buildings, and place context. Prefer steward-approved existing information over a nationwide default. Preserve field-level provenance and unresolved conflicts.
3. **Build candidate layers and a gap report.** Suggest road matches, address-to-road relationships, and possible missing sites. Do not fabricate authoritative address ranges from nearby address minima/maxima, treat every footprint centroid as an entrance, or substitute administrative divisions for emergency-service boundaries.
4. **Review uncertainty on the map.** Show missing source evidence, stale records, ambiguous addresses, duplicate candidates, disconnected access, and jurisdiction conflicts as a prioritized work queue. “Needs field verification” should be a useful state, not a hidden null or a synthetic confidence percentage.
5. **Validate and export a preparation package.** Include schema/domain checks, geometry errors, duplicate identifiers, address/road inconsistencies, source coverage, boundary disagreement, routing connectivity, and unresolved issues. Make results reproducible and include the exact input releases and transformations. The package should say “Foundation for authority review.”
6. **Support operational acceptance separately.** Enable an authority to record reconciliation outcomes, provider acceptance, ownership, update cadence, and version rollback. Do not ship an automatic “dispatch ready” score or imply that passing structural tests establishes field accuracy. Federal guidance describes GIS/MSAG/ALI reconciliation and neighboring PSAP boundary coordination as part of readiness. [National 911 Program case study](https://www.911.gov/newsletters/issue-3/local-ng911-and-national-address-database-initiatives-show-promise/)

Potential local extensions to design with a pilot agency: entrance/access-point candidates; address-to-entrance-to-road relations; observed gates and access constraints; field-verification evidence; effective dates; reviewed source matches; and agency routing overrides. Keep candidate observations distinct from approved operational facts. Public basemap improvements can be proposed upstream once reviewed and licensed for sharing; operational evidence may need to remain local.

## Proposed delivery order and completion evidence

| Milestone | Reviewable output | Completion evidence |
| --- | --- | --- |
| 1. Provenance and correction drafts | Feature inspection, immutable source references, editable overlay, correction export | A user can explain where a value came from and reproduce a proposed change after reopening the project. |
| 2. Study network pilot | Regional graph package, adapter manifest, route/isochrone layers | Restriction fixtures pass, unresolved semantics are visible, and offline results reproduce. |
| 3. NG911 preparation pilot | Versioned target profile, field crosswalk, candidates and gap queue | A participating GIS/911 steward can review every inferred field and missing source. No output claims operational approval. |
| 4. Contribution and updates | Reviewed contribution package, release reconciliation, rollback | Upstream submission and later incorporation are independently tracked; local approved edits survive refresh without silent overwrite. |

The unresolved implementation questions are OMF-Bifrost restriction coverage and supported releases, a supportable Windows packaging strategy, native ArcGIS network connectivity translation, the pilot jurisdiction's adopted profile, and real local-data quality. Resolve these with a small representative county or city before promising national automated NG911 generation.
